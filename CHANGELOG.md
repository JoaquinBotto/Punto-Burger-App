# Changelog

Todos los cambios notables de este proyecto se documentarán en este archivo.

El formato está basado en [Keep a Changelog](https://keepachangelog.com/es-ES/1.0.0/), y este proyecto adhiere de manera semántica a su evolución.

## [Unreleased]

### Added

- `PPA-010`: Acceso a Mesa, Código Temporal y Sesión. Implementación completa del primer flujo interactivo autoservicio de Punto Burger: ruta pública de mesa `GET /table/[tableCode]` (con resolución server-side de local y mesa, e interfaz mobile-first con estados: disponible, ocupada, en preparación temporal, deshabilitada e inexistente); endpoint de claim `POST /api/v1/tables/claim` con validación Zod y rate limiting en memoria (máximo 5 intentos fallidos consecutivos por IP y mesa); validación determinística HMAC-SHA256 de código temporal de local (rotación cada 5 min y 45s de gracia para ventana anterior); transacción atómica en PostgreSQL (`table_sessions`, `devices`, asignación de `active_device_id`, actualización de mesa a `in_use` y registro de auditoría inmutable `session_created`); emisión de cookie de control segura `pb_table_session` (HttpOnly, SameSite=Lax, Path=/, duración 90 minutos) almacenando exclusivamente el hash SHA-256 del token en la base de datos; recuperación de sesión transparente e idempotente ante recargas del mismo navegador; rechazo de dispositivos concurrentes (`TABLE_ALREADY_IN_USE` respaldado por índice parcial único en PostgreSQL); rechazo de dispositivo con sesión activa en otra mesa (`DEVICE_HAS_ACTIVE_SESSION`); normalización perezosa (lazy normalization) de sesiones expiradas y mesa en cooldown (2 minutos) con auto liberación sin intervención de mozos; pantalla preparatoria `/play/setup`; herramienta CLI de desarrollo `npm run dev:access-code -- esperanza-central`; suite de 80 pruebas automatizadas y validación real completa en DonWeb Cloud Server aprobada (`PPA-010 PRODUCTION SMOKE TEST = PASSED`), documentada en `docs/implementation/PPA-010-table-access.md`.

- `INFRA-001`: Preparación para Deployment Automatizado a DonWeb Cloud Server. Configuración completa del pipeline de CI/CD para producción bajo el dominio oficial `https://app.puntoburger.com.ar` sin uso de Vercel; definición estricta de Drizzle como único sistema oficial de migraciones (`ONE DATABASE MIGRATION SYSTEM = DRIZZLE`); creación del workflow de GitHub Actions (`.github/workflows/deploy-production.yml`) con control de concurrencia y validación obligatoria previa (lint, typecheck, tests, build y verificación de esquemas); configuración de Nginx virtual host (`deploy/nginx/app.puntoburger.com.ar.conf`) con reverse proxy a 127.0.0.1:3000, soporte Certbot, caché inmutable en `/_next/static/` y restricción estricta de caché para `/api/*`, `/table/*` y `/play/*`; configuración de supervisión PM2 (`ecosystem.config.cjs`); scripts de aprovisionamiento (`deploy/scripts/bootstrap-server.sh`), activación atómica de releases (`deploy/scripts/deploy-release.sh`) con conservación de los últimos 5 releases, y reversión de emergencia (`deploy/scripts/rollback-release.sh`); documentación integral de infraestructura y runbook operativo en `docs/deployment/donweb-production.md`.
- `PPA-009`: Supabase, Drizzle, Modelo Inicial y Seeds. Implementación de la capa de persistencia relacional con Drizzle ORM y Postgres.js (`postgres`); modelado de las 13 entidades fundacionales del Vertical Slice (`venues`, `tables`, `access_codes`, `table_sessions`, `devices`, `groups`, `participants`, `categories`, `questions`, `game_sessions`, `game_questions`, `answers`, `audit_events`) con UUIDs nativos, marcas de tiempo `timestamptz`, políticas de eliminación seguras (`restrict` para preservar historial, `cascade` únicamente para entidades acopladas al ciclo de sesión) e índice único parcial en PostgreSQL (`table_sessions` activas por mesa); foreign key de `table_sessions.active_device_id` hacia `devices.id` con `onDelete: 'set null'`; diseño e implementación del esquema determinístico HMAC-SHA256 para códigos temporales de local (rotación cada 5 minutos, ventana de gracia de 45 segundos, alfabeto sin ambigüedades y derivación independiente de estado en memoria); configuración de Drizzle Kit y generación de migración inicial SQL versionada (`src/db/migrations/0000_lonely_slayback.sql`); seed idempotente con local oficial Punto Burger Esperanza, Mesa 01, 6 categorías temáticas y 72 preguntas aprobadas y balanceadas por dificultad (12 por categoría: 4 initial, 4 medium, 4 advanced) asegurando partidas completas 3/4/3 por tema individual; repositorios de dominio para venues, tables, categories y questions; helpers de seguridad para hashing de tokens (`sha256` con protección contra timing attacks); cliente administrativo server-side de Supabase; suite de 47 pruebas automatizadas (12 suites unitarias en Vitest) y documentación técnica en `docs/implementation/PPA-009-database.md`.
- `PPA-008`: Bootstrap del Proyecto Punto Burger. Inicialización de la aplicación web full-stack con Next.js 16 (16.4.5, App Router), React 19, TypeScript estricto, Tailwind CSS, Zod, ESLint 9 (Flat Config), Prettier y Vitest; implementación de la arquitectura de Monolito Modular con límites de dominio (`venues`, `tables`, `sessions`, `groups`, `trivia`, `identity`, `schools`, `rewards`); esquema de validación estricta de variables de entorno en runtime mediante Zod (`src/lib/env`); endpoint diagnóstico y health check `GET /api/health` respondiendo en formato JSON estándar; landing page inicial Mobile First para Punto Burger en Esperanza, Santa Fe; suite inicial de pruebas unitarias automatizadas (15 tests en 5 suites); pipeline de Integración Continua en GitHub Actions (`.github/workflows/ci.yml`); documentación completa de desarrollo local en `README.md` e informe de implementación en `docs/implementation/PPA-008-bootstrap.md`.

### Changed

- `Hotfix INFRA-001`: Modernización de API Keys de Supabase, corrección de conexión PostgreSQL y endurecimiento del bootstrap para DonWeb Cloud Server antes del primer despliegue. Migración integral de variables de autenticación a `SUPABASE_PUBLISHABLE_KEY` (reemplaza a `SUPABASE_ANON_KEY`) y `SUPABASE_SECRET_KEY` (reemplaza a `SUPABASE_SERVICE_ROLE_KEY`) en el validador de runtime Zod (`src/lib/env/index.ts`), cliente administrativo server-side (`src/lib/supabase/admin.ts`), pruebas unitarias asociadas, plantilla `.env.example`, `README.md`, script de aprovisionamiento `deploy/scripts/bootstrap-server.sh` y guías operativas. Corrección de la arquitectura de conexión PostgreSQL en DonWeb Cloud Server (Ubuntu 24.04 con IPv6 funcional) estableciendo Direct Connection Supabase en puerto `:5432` tanto para `DATABASE_URL` como para `DATABASE_MIGRATION_URL`, eliminando referencias a Transaction Pooler (`:6543`) y documentando Session Pooler (`:5432`) como fallback ante eventuales entornos IPv4 puros. Endurecimiento de `deploy/scripts/bootstrap-server.sh` con parametrización de `SSH_PORT` (por defecto 5098 en DonWeb), habilitación del puerto SSH en UFW previa activación para prevenir bloqueos de acceso, y eliminación de `apt-get upgrade -y` automático en servidores existentes. Ajuste del workflow `.github/workflows/deploy-production.yml` con fallback de puerto SSH a 5098. Reconfirmación de que las credenciales privilegiadas y secretos de sesión permanecen exclusivamente en el entorno del servidor y nunca se exponen al cliente.
- `Hotfix post-PPA-008`: Unificación oficial del runtime en **Node.js 24 LTS** (actualización de `.nvmrc` a `24`, declaración de `engines` en `package.json` a `>=24 <25`, actualización de runner en `.github/workflows/ci.yml` a Node 24 y alineación unificada para desarrollo, CI y DonWeb Cloud Server). Corrección de accesibilidad en `src/app/layout.tsx` eliminando `maximumScale: 1` y `userScalable: false` para permitir el zoom del navegador en dispositivos móviles de acuerdo con pautas de accesibilidad, incorporando test unitario en `src/app/layout.test.ts`.
- `specs/06-technical-architecture.md` (`PPA-007`) especificación técnica y de arquitectura completa revisada y aprobada oficialmente (v1.0.0). Define el stack definitivo Full-Stack TypeScript (Next.js 16.x estable / Active LTS, Tailwind CSS, Zod, PostgreSQL en Supabase gestionado, Drizzle ORM y Supabase Auth); arquitectura de producción orientada a servidor Linux persistente en DonWeb Cloud Server con Nginx como reverse proxy/TLS y PM2 como supervisor de procesos; aislamiento estricto de base de datos sin acceso directo del cliente a Supabase Data API; autenticación limpia de invitados vía cookie de sesión propia emitida por el servidor (sin crear usuarios anónimos en Supabase Auth); separación de conexiones de runtime (`DATABASE_URL`) y migraciones (`DATABASE_MIGRATION_URL`); APIs de juego versionadas en Route Handlers (`/api/v1/*`) delegando en servicios de dominio; temporizador autoritativo server-side (`expires_at`) sin tolerancia fija obligatoria; modelo multi-local mediante foreign key `venue_id`; esquema de base de datos incremental (13 entidades iniciales para el prototipo); estrategia de CI/CD vía GitHub Actions y deploy SSH a DonWeb; definición de los 19 puntos del Vertical Slice y plan de tickets (PPA-008 a PPA-015).
- `docs/adr/001-technology-stack.md`: Registro formal de decisión arquitectónica (ADR 001, Aprobado) documentando la selección de Next.js 16 + DonWeb Cloud Server (Nginx + PM2) con Supabase PostgreSQL & Auth, registrando el descarte formal de Vercel, Laravel y React/Vite.
- `specs/05-users-schools-consent.md` (`PPA-006`) especificación funcional completa revisada, ampliada y aprobada oficialmente (v1.0.0). Incorpora el sistema de usuarios persistentes, historial entre visitas, estadísticas personales y separación de tres tipos de puntuación (partida, progresión personal y contribución competitiva); define el modelo de competencia entre escuelas y cursos con regla de equidad (mejor partida por usuario en el período y promedio del curso para neutralizar el sesgo demográfico), umbral de clasificación oficial (5 usuarios únicos) y estado provisional; cálculo del ranking de escuelas como promedio de cursos elegibles y enfrentamientos internos dentro de un mismo colegio; sistema de temporadas con congelamiento y archivo histórico inmutable; perfiles públicos de curso y escuela con protección de menores (sin listados nominales); difusión motivacional en pantallas físicas del bar; consentimientos modulares e independientes; seis estados de cuenta; flujos funcionales A–I y 23 casos límite.
- `specs/04-qr-table-access.md` (`PPA-005`) revisado y aprobado oficialmente (v1.0.0). Revisión estructural: modelo autoservicio sin activación manual del personal; mecanismo QR + código temporal autónomo; cuatro estados de mesa (Deshabilitada, Disponible, En uso, Liberación temporal); liberación automática de 2 minutos. Aclaraciones finales incorporadas: el código se valida solo al crear la sesión y no la interrumpe una vez activa; tolerancia de 30–60 s durante la rotación para evitar rechazos; referencia funcional de 2 minutos para el período de liberación con reglas explícitas; visualización autónoma del código en pantallas físicas del local sin acción recurrente del personal.
- Especificación funcional de mecánica de juego y reglas operativas (`PPA-004`) revisada y aprobada oficialmente (v1.0.0). Correcciones aplicadas: límite efectivo de 8 participantes registrados con comportamiento claro para mesas con más personas; segundo dispositivo informado y con flujo de transferencia de control diferido a PPA-005; registro de respuestas sin asumir arquitectura en tiempo real; temporizador inmutable durante recuperaciones; alcance del ranking acotado a partidas de juego con fidelización diferida; comportamiento explícito de las opciones "Finalizar sesión" y "Continuar en modo práctica".
- Especificación de MVP y Roadmap (`PPA-003`) revisada y aprobada oficialmente (v1.0.0). Define el alcance de la validación interna, el lanzamiento público (incluyendo escuelas e IA) y el roadmap general sin ataduras tecnológicas.
- Especificación funcional de visión de producto (`PPA-002`) revisada y aprobada oficialmente (v1.0.0). Documenta el propósito, objetivos y límites del ecosistema de Punto Burger, priorizando a las escuelas desde el lanzamiento público.
